## Why this study

We want to build a Rust PDF validator with both a reusable library API and a CLI. The useful question is not "how does veraPDF work" broadly, but: which architectural boundaries, data shapes, and validation traversal rules should a Rust implementation copy, adapt, or avoid?

## Architecture map

```text
CLI app
  vendors/veraPDF-apps/cli
    GreenfieldCliWrapper -> registers Greenfield foundry, then delegates to VeraPdfCli
    VeraPdfCli -> parses args, selects single-process or multi-process runner
    VeraCliArgParser -> builds ValidatorConfig, AppConfig, ProcessorConfig
        |
Library facade
  vendors/veraPDF-library/core
    ProcessorFactory -> creates ProcessorConfig, ItemProcessor, BatchProcessor, report handlers
    ProcessorImpl -> parse, validate, extract features, fix metadata
    ValidationProfile / Rule -> profile objects loaded from XML resources
    BaseValidator / FlavourValidator -> graph traversal and rule execution
        |
Validation binding
  vendors/veraPDF-validation/validation-model
    VeraGreenfieldFoundryProvider -> registers VeraFoundry as default
    VeraFoundry -> creates GFModelParser and validators
    GFModelParser -> parses PDDocument and exposes model root
    GFPD* / GFCos* objects -> validation-model wrappers around parser objects
        |
Parser
  vendors/veraPDF-parser
    PDDocument -> catalog-level document facade
    COSDocument -> header/body/xref/trailer/resource owner
    PDFParser / SeekableCOSParser -> syntax, xref, object, stream parsing
    COSObject / COSStream -> dynamically typed object facade over concrete COS bases
```

The central boundary is the `PDFAParser`/foundry boundary. The app does not construct parser internals directly. The CLI wrapper registers the Greenfield foundry before calling the main CLI (`vendors/veraPDF-apps/cli/src/main/java/org/verapdf/apps/GreenfieldCliWrapper.java:51`). The provider installs itself through `Foundries.registerDefaultProvider` (`vendors/veraPDF-validation/validation-model/src/main/java/org/verapdf/gf/foundry/VeraGreenfieldFoundryProvider.java:33`), and `VeraFoundry` creates `GFModelParser` instances from files or streams (`vendors/veraPDF-validation/validation-model/src/main/java/org/verapdf/gf/foundry/VeraFoundry.java:60`, `vendors/veraPDF-validation/validation-model/src/main/java/org/verapdf/gf/foundry/VeraFoundry.java:95`).

For Rust, the equivalent boundary should be an explicit `ValidatorEngine`/`PdfParser` API rather than global registration. The library should expose stable config/result types and keep parser/model internals behind crate-private modules.

## Key data structures

`ProcessorConfig` and `VeraAppConfig`: the public control plane. veraPDF keeps app config and processor config separate: app config controls output/report behavior while processor config controls validation tasks. This is useful for Rust because the library should not depend on CLI concerns, but the CLI should be a thin config adapter.

`ValidationProfile`: immutable profile data keyed by `PDFAFlavour`. Built-in profiles are loaded from XML resources during default directory construction by iterating `PDFAFlavour.values()` and resource paths (`vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/profiles/ProfileDirectoryImpl.java:50`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/profiles/ProfileDirectoryImpl.java:154`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/profiles/ProfileDirectoryImpl.java:156`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/profiles/ProfileDirectoryImpl.java:158`). Rust should compile known profiles into static data after an offline generation step, but still support loading custom profile files.

`COSObject`: a dynamic facade over concrete COS bases. It supports empty objects, typed getters/setters, stream data access, indirect references, and dictionary/array operations (`vendors/veraPDF-parser/src/main/java/org/verapdf/cos/COSObject.java:57`, `vendors/veraPDF-parser/src/main/java/org/verapdf/cos/COSObject.java:79`, `vendors/veraPDF-parser/src/main/java/org/verapdf/cos/COSObject.java:98`, `vendors/veraPDF-parser/src/main/java/org/verapdf/cos/COSObject.java:350`, `vendors/veraPDF-parser/src/main/java/org/verapdf/cos/COSObject.java:440`). Rust should model this as an enum plus typed accessors returning `Result` or `Option` depending on whether absence is legal; validation-specific parse defects should be retained as structured metadata.

`COSStream`: stores dictionary plus an input stream and filter state, and creates filtered data streams on demand (`vendors/veraPDF-parser/src/main/java/org/verapdf/cos/COSStream.java:83`, `vendors/veraPDF-parser/src/main/java/org/verapdf/cos/COSStream.java:143`, `vendors/veraPDF-parser/src/main/java/org/verapdf/cos/COSStream.java:157`, `vendors/veraPDF-parser/src/main/java/org/verapdf/cos/COSStream.java:163`). Rust should avoid eager stream decompression; expose raw and decoded readers with byte limits.

`BaseValidator` object stack: validation is a graph walk, not a recursive descent. It uses `objectsStack`, `objectsContext`, and `idSet` to avoid reprocessing objects with IDs (`vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:63`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:72`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:177`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:327`). Rust should copy the explicit stack and visited-set approach to avoid deep recursion and stack exhaustion on hostile PDFs.

Thread-local static caches: veraPDF stores current document, flavour, CMaps, fonts, role maps, color spaces, glyphs, and other per-document state in `ThreadLocal` containers (`vendors/veraPDF-parser/src/main/java/org/verapdf/tools/StaticResources.java:50`, `vendors/veraPDF-parser/src/main/java/org/verapdf/tools/StaticResources.java:55`, `vendors/veraPDF-validation/validation-model/src/main/java/org/verapdf/gf/model/impl/containers/StaticContainers.java:37`, `vendors/veraPDF-validation/validation-model/src/main/java/org/verapdf/gf/model/impl/containers/StaticContainers.java:45`, `vendors/veraPDF-validation/validation-model/src/main/java/org/verapdf/gf/model/impl/containers/StaticContainers.java:57`). This is a major pattern to avoid in Rust.

## Key algorithms

Flavour detection: if the caller requests `NO_FLAVOUR`, the parser reads XMP metadata from the catalog and returns detected PDF/A, PDF/UA, and WTPDF flavours; if metadata is absent or invalid, it falls back to the configured default (`vendors/veraPDF-validation/validation-model/src/main/java/org/verapdf/gf/model/GFModelParser.java:105`, `vendors/veraPDF-validation/validation-model/src/main/java/org/verapdf/gf/model/GFModelParser.java:167`, `vendors/veraPDF-validation/validation-model/src/main/java/org/verapdf/gf/model/GFModelParser.java:184`, `vendors/veraPDF-validation/validation-model/src/main/java/org/verapdf/gf/model/GFModelParser.java:191`). Rust should make this a first-class `FlavourSelection::{Auto { default }, Explicit, CustomProfile }` enum.

Profile compatibility filtering: `BaseValidator` creates one `FlavourValidator` per profile only when detected profiles share the same PDF specification version; incompatible flavours are skipped with a warning (`vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:103`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:107`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:112`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:115`). Rust should return a structured warning in the validation report, not just log it.

Validation traversal: each object is checked against rules for its concrete type and supertypes, variables are updated after rule checks, linked objects are pushed in reverse order, and deferred rules run after traversal (`vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:190`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:331`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:338`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:352`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:276`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:290`). Rust should preserve the deterministic context paths because they are part of useful diagnostics.

Failure reporting: the validator increments a total test counter, tracks per-rule failed counts, caps displayed failures, and optionally records passed assertions (`vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:55`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:56`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:376`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:381`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:383`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:394`). Rust should expose both machine-complete counters and bounded assertion details.

Tolerant parse with compliance facts: the parser does not just accept or reject. It records exact facts such as header offset, stream length mismatch, stream keyword EOL compliance, real stream size, xref marker compliance, and post-EOF data. Rules can then assert on these facts. Rust should treat parser anomalies as facts attached to objects, not only as errors.

## What we will adopt

Adopt the library-first shape: a stable library facade should own `ValidatorConfig`, `ValidationProfile`, `ValidationReport`, `BatchReport`, `Format`, and `validate_file`/`validate_reader` entrypoints. The CLI should only parse arguments, call the library, and format reports. `ProcessorFactory` and `ProcessorImpl` prove this split works (`vendors/veraPDF-library/core/src/main/java/org/verapdf/processor/ProcessorFactory.java:95`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/processor/ProcessorImpl.java:103`).

Adopt a foundry-like internal boundary, but make it explicit and typed. Use traits such as `PdfParser`, `ValidationModel`, and `RuleEvaluator` inside the crate so the CLI never depends on parser modules. Avoid runtime global provider registration.

Adopt iterative graph traversal with object type, supertypes, link names, context path, deferred rules, and visited IDs. This is load-bearing for validation correctness and diagnostics (`vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:184`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:331`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:352`).

Adopt profile-driven validation. Profiles should remain data, not hand-coded Rust checks. For initial implementation, compile official profiles into generated Rust data and keep custom profile loading as a later phase.

Adopt tolerant parsing that preserves anomalies as queryable facts. A strict parser alone cannot validate conformance because many rules depend on malformed-but-parseable details like stream spacing and length behavior (`vendors/veraPDF-parser/src/main/java/org/verapdf/parser/SeekableCOSParser.java:190`, `vendors/veraPDF-parser/src/main/java/org/verapdf/parser/SeekableCOSParser.java:205`, `vendors/veraPDF-parser/src/main/java/org/verapdf/parser/SeekableCOSParser.java:232`).

Adopt output formats as a library concern, but keep transport out. veraPDF supports text, raw, XML/MRR, HTML, and JSON via report handlers (`vendors/veraPDF-library/core/src/main/java/org/verapdf/processor/ProcessorFactory.java:128`). Rust should start with JSON and text; XML/MRR compatibility can be a separate spec.

## What we will avoid

Avoid `ThreadLocal` document state and static mutable caches. veraPDF clears and reinitializes static containers before parse (`vendors/veraPDF-validation/validation-model/src/main/java/org/verapdf/gf/model/GFModelParser.java:80`, `vendors/veraPDF-validation/validation-model/src/main/java/org/verapdf/gf/model/GFModelParser.java:246`), then sets document/flavour into thread-local state (`vendors/veraPDF-validation/validation-model/src/main/java/org/verapdf/gf/model/GFModelParser.java:230`, `vendors/veraPDF-validation/validation-model/src/main/java/org/verapdf/gf/model/GFModelParser.java:293`). In Rust this should be a `ValidationSession` that owns caches explicitly and is `Send` only if its internals are actually safe.

Avoid JavaScript rule execution in-process unless sandboxed. veraPDF evaluates profile expressions through `JavaScriptEvaluator` (`vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:232`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/pdfa/validation/validators/BaseValidator.java:363`). For Rust, prefer a small expression IR generated from profiles, with bounded evaluation and no ambient host access.

Avoid using panics or process exits in the library. veraPDF catches `OutOfMemoryError` in the CLI/processor (`vendors/veraPDF-library/core/src/main/java/org/verapdf/processor/ProcessorImpl.java:141`, `vendors/veraPDF-apps/cli/src/main/java/org/verapdf/cli/VeraPdfCli.java:118`). Rust cannot recover from all allocation failures, but parse/resource limits should be explicit config and ordinary errors.

Avoid multi-process as the first concurrency story. veraPDF CLI has a process-count option and a multi-process path (`vendors/veraPDF-apps/cli/src/main/java/org/verapdf/cli/VeraPdfCli.java:111`, `vendors/veraPDF-apps/cli/src/main/java/org/verapdf/cli/commands/VeraCliArgParser.java:206`). A Rust validator should first make per-file sessions independent and run bounded parallel file validation with worker tasks or threads.

Avoid metadata fixing and feature extraction in the initial validator core. veraPDF supports them as processor tasks (`vendors/veraPDF-library/core/src/main/java/org/verapdf/processor/ProcessorImpl.java:121`, `vendors/veraPDF-library/core/src/main/java/org/verapdf/processor/ProcessorImpl.java:124`). They are separate products from validation and will complicate a first Rust validator.
